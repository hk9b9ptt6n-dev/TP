## Работа 1. CVE-2026-86950: учебный разбор - от статьи к прототипу

### Поиск информации

Пользуясь агрегаторами уязвимостей (NVD, CVE Details, каталог CISA KEV), мы
сверили номер CVE-2026-86950 ещё до чтения технических материалов. Карточка

- **Вендор / продукты:** Apple; iOS и iPadOS
- **Дата публикации:** 28.09.2026
- **Тип:** запись за границами массива (out-of-bounds write), исправлено улучшенной проверкой границ
- **CVSS 3.1:** 8.8 (HIGH), вектор `AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:H`
- **EPSS:** 1,24%
- **CISA KEV:** да — номер числится в каталоге реально эксплуатируемых уязвимостей
- **Исправлено в:** iOS/iPadOS 26.7.1, macOS Sequoia 15.8.1, macOS Tahoe 26.7.1
- **Особая отметка в карточке:** по данным вендора, уязвимость использовалась в крайне сложных атаках на конкретных людей

Уязвимость все еще актуальна

### Механизм уязвимости простыми словами

Разбор опирается на публикацию calif.io
[«The Great Glyph Grift»](https://calif.io/research/the-great-glyph-grift) (30.09.2026) и данные [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-86950).

В растеризаторе CoreGraphics - компоненте Apple, который рисует векторную
графику и шрифты, есть функция `aa_double_to_fixed()`. Она переводит
координаты из дробных чисел в целочисленный фиксированный" формат умножением
на 4096 и не проверяет результат на переполнение:

```c
static inline int32_t aa_double_to_fixed(double px) {
    double v = 0.5 + 4096.0 * px;   // ×4096 - переход к fixed-point 
    return (int32_t)v;              // приведение без проверки границ 
}
```

Если координата больше 524 288 пикселей (2^19), произведение перестаёт
помещаться в 32-битное целое число. Дальше важно, чтов двух соседних шагах
рендеринга результат обрабатывается разными процессорными инструкциями - одна
«насыщает» значение на границе, другая молча обрезает. Из-за этого расхождения
ломается расчёт границ глифа: граница получается Уже, чем нарисованные рёбра,
рендерер выделяет под неё буфер памяти меньше необходимого, а пишет в него по
фактическому количеству рёбер  - тем самым выходя за границы буфера.

ДЛя того, чтобы запустить достаточно обычного PDF со встроенным шрифтом: при
отображении документа рендерер обрабатывает специально подготовленный глиф -
его координаты увеличиваются примерно в 127 раз через семь вложенных уровней
масштабирования и попадает на уязвимый код. Открываться файл может где
угодно: Preview.app (встроенный просмотрщик от Apple), вложение в Telegram или IMessage. В сценарии с вложениями система сама строит миниатюру файла - жертве не нужно ничего нажимать.

### Прототип: что нам удалось получить

Следуя методике из статьи, мы получили учебный прототип первых трёх этапов
цепочки. Файлы генерации PDF приложены в репозитории (папка `prototypeCVE/`).
Происхождение прототипа  - по  опубликованному описанию - не копия чужого кода и не
разработка "с нуля", а собранные по открытым материалам скрипты, которые мы
использовали для разбора.

Что делает прототип:
1. подготавливает шрифт с координатами, увеличенными через вложенные уровни
   масштабирования;
 • Цепочка составных глифов с контролируемым масштабированием         
 • Вызывает переполнение int32 в функции aa_double_to_fixed()      
 • Различие между насыщением (saturation) и усечением (truncation) приводит к  повреждение ограничивающего прямоугольника (bbox) 
   Выходной файл: trigger.ttf     
   
2. встраивает его в PDF;
 • Отрисовка 256 глифов для подготовки кучи (heap grooming)        
 • Инициирование использования глифа после его освобождения (use-after-free) для вызова сбоя 
  Выходной файл: trigger.pdf
  
3. вызывает рендеринг документа.
 • Инициирует отрисовку шрифтов через CoreGraphics                 
 • aa_cache_render(): запись за пределами буфера (OOB write) в буфер покрытия (coverage buffer) 
 Сбой

4. Если бы уязвимая версия получила такой документ, из дампа краша можно было

   Стратегия B: Повреждение указателя на объект                      
  • Перезапись таблицы виртуальных функций (vtable) или указателя на функцию 
  • Последующий вызов виртуальной функции -> выполнение кода
